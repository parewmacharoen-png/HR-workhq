# WorkHQ — Database Migrations

This directory is the **migration baseline** for the WorkHQ platform. It is a
hand-authored, validated baseline rather than a Prisma-autogenerated one,
because the schema relies on PostgreSQL features that Prisma's schema language
cannot express (EXCLUDE constraints, partial unique indexes, triggers,
functions, and a `pgvector` HNSW index).

Both migration files have been applied, in order, to a clean **PostgreSQL
16.14** instance with `ON_ERROR_STOP=1` and verified to produce:
74 tables · 70 triggers · 2 EXCLUDE constraints · 2 trigger functions ·
soft-delete-aware partial unique indexes · 1 HNSW vector index.

---

## Directory structure

```
prisma/
├── schema.prisma                         # 74 models, 40 enums, 19 @@schema
└── migrations/
    ├── migration_lock.toml               # provider = "postgresql"
    ├── 20260101000000_init/
    │   └── migration.sql                 # Prisma-representable objects
    └── 20260101000100_pg_features/
        └── migration.sql                 # PostgreSQL-only objects
```

Prisma applies migrations in **lexicographic order of folder name**, so the
`init` migration (timestamp `…000000`) always runs before `pg_features`
(timestamp `…000100`). The 100-second gap in the timestamps guarantees that
ordering forever.

## What is in each migration

### `20260101000000_init/migration.sql`

Everything Prisma's own migration engine could also generate:

| Object | Count |
|---|---|
| Extensions (`pgcrypto`, `btree_gist`, `vector`) | 3 |
| Schemas (one per domain) | 19 |
| Enum types | 40 |
| Tables (with inline `CHECK`, `UNIQUE`, `FK`) | 74 |
| Plain (non-partial) indexes | 84 |
| Deferred-FK `ALTER TABLE` statements | 6 |

**EXCLUDE constraints note:** `ex_salary_no_overlap` and
`ex_formula_no_overlap` are defined **inline** in their `CREATE TABLE`
statements here. They are valid PostgreSQL and apply correctly, but Prisma's
schema language cannot model them — see *Drift management* below.

### `20260101000100_pg_features/migration.sql`

The objects Prisma **cannot represent at all** and would silently drop on a
`prisma migrate diff`. Isolated here so the boundary is explicit and auditable:

| Object | Detail |
|---|---|
| Trigger functions | `system.set_updated_at()`, `system.forbid_mutation()` |
| Triggers (70) | `updated_at` maintenance on every business table; **append-only** enforcement (blocks `UPDATE`/`DELETE`) on `audit_logs`, `workflow_actions`, `recruitment_pipeline_events` |
| Partial unique indexes | soft-delete-aware uniqueness (`WHERE deleted_at IS NULL`) and other conditional uniqueness (e.g. one active primary assignment per employee, one open break per record) |
| pgvector HNSW index | `ai.ai_embeddings.embedding` with `vector_cosine_ops` |

## Why a hand-authored baseline (and not `prisma migrate dev`)

`prisma migrate dev` generates `migration.sql` by diffing `schema.prisma`. That
diff **cannot see** EXCLUDE constraints, partial indexes, triggers, functions,
or the HNSW index, so a generated baseline would be missing every guarantee in
`pg_features` plus the two EXCLUDE constraints. Authoring the baseline from the
validated DDL preserves all of them.

Prisma's `migrate deploy` does **not** require migrations to be
Prisma-generated — it executes each `migration.sql` verbatim and records it in
the `_prisma_migrations` table. This baseline is therefore fully compatible
with the normal Prisma deploy workflow.

---

## Drift management (important)

Because `schema.prisma` cannot model EXCLUDE constraints, partial indexes,
triggers, or functions, a naive `prisma migrate dev` in the future may try to
"fix" perceived drift. Follow these rules:

1. **Never** run `prisma migrate dev` against a database that already has this
   baseline applied without first reviewing the generated SQL. If Prisma
   proposes dropping a trigger, function, partial index, or EXCLUDE
   constraint, **delete those lines** from the generated migration before
   committing.

2. For each **new** schema change going forward:
   - Make the model change in `schema.prisma`.
   - Run `prisma migrate dev --create-only` to generate the migration **without
     applying it**.
   - Hand-edit the generated `migration.sql` to add any PostgreSQL-only
     objects the change requires (new triggers, partial indexes, etc.).
   - Apply with `prisma migrate dev` (or `deploy` in CI).

3. The `system.*` trigger functions and the append-only triggers are
   **infrastructure invariants** — they should only ever be modified through an
   explicit, reviewed migration, never regenerated.

## Verifying a fresh apply locally

```bash
# Against a throwaway database (psql path shown for PG 16):
createdb workhq_verify
psql -d workhq_verify -v ON_ERROR_STOP=1 -f migrations/20260101000000_init/migration.sql
psql -d workhq_verify -v ON_ERROR_STOP=1 -f migrations/20260101000100_pg_features/migration.sql

# Spot-check the guarantees:
psql -d workhq_verify -c "SELECT count(*) FROM pg_constraint WHERE contype='x';"   -- expect 2
psql -d workhq_verify -c "SELECT count(*) FROM information_schema.triggers;"        -- expect 70
psql -d workhq_verify -c "INSERT INTO system.audit_logs(entity_type,action) VALUES('x','y'); UPDATE system.audit_logs SET action='z';"
#   -> ERROR: Table system.audit_logs is append-only; UPDATE is not permitted
```
